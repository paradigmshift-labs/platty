# 답변 형식

## 1. 구성: 두 층

답은 두 층이다. **1층**은 현업이 읽는 짧은 답, **2층**은 검수자·개발자가 읽는 첨부다. 조사 과정과 근거는 지금처럼 모두 하고 표시 형식만 이렇게 나눈다. 1층의 모든 문장은 2층 `근거 표`의 한 행이다.

### 1층 (현업이 읽는 부분)

```markdown
# <메뉴 경로> > <화면 title> (<화면 ID>) — <질문 요지 한 줄>

해석: <앵커 후보가 갈려 하나를 고른 경우에만 한 줄>

**한 줄 답**: <직접 답 한 문장. 예/아니오/부분. 업무 말로. 숫자가 있으면 합친 최종 개수>

**핵심 정리** (값·조건을 열거하는 질문일 때만)
| 값 | 조건 | 확인되는 때 | 입력 방법 |
|---|---|---|---|

**이렇게 하세요** (동작·위치 질문일 때, 최대 4개)
1. 「메뉴 경로」 > 화면 > 버튼·항목 이름: 할 일

**막히는 경우** (최대 4개)
- <조건을 화면에 보이는 말로. 읽은 오류 문구가 있으면 따옴표로>

**다른 방법** (있을 때)
- 「메뉴 경로」 > 화면: 무엇을 하는지 업무 말로. 어느 쪽이 처리 절차인지는 업무 정책이라 코드로 알 수 없습니다.

**확인이 필요한 것**: <한 줄. 운영 설정값·권한·정책이면 "담당 부서에 확인이 필요합니다.">
```

1층 규칙
- 분량은 표를 빼고 약 700자, 단계는 4개 이하. 질문이 묻는 것만 쓴다. 묻지 않은 사실은 쓰지 않고, 답을 바꾸는 단서만 한 줄로 붙인다.
- **쓰지 않는 것**: 테이블·컬럼·필드 이름, API 경로, 메시지 ID, 파일 경로, 호출 수, 이 스킬의 규칙 용어, 분석 도구의 표시(`deprecated`, 후보 구현), `[확정]` 같은 확신도 표기. 화면 ID는 제목의 괄호에 한 번만 쓴다. 이 모두는 2층에 정확히 쓴다.
- 화면에 찍힌 낱말(라벨, 메뉴·화면 title, 알림 문구)은 읽은 줄에서 그대로 인용해 쓴다. 따옴표 안의 라벨은 읽은 `text`·`title` 줄, 따옴표 안의 메시지는 알림 호출에 넘긴 문자열이나 메시지 테이블 행에서만 가져온다. 코드 옆 주석은 메시지가 아니다.
- 코드값의 뜻은 용어 카드·공통코드·상수 정의 같은 출처가 있을 때만 쓴다. 없으면 "해당 값"으로 쓰고 2층에 "코드값의 뜻은 확인하지 못함"을 쓴다. 코드값이 사람이나 역할을 뜻한다고 쓰지 않는다.
- 비교는 낱말로 쓴다: `<` 미만(그날 제외), `<=` 이하(그날 포함), 초과, 이상. "이전/이후"만 쓰지 않는다. 화면 문구와 실제 조건이 다르면 둘 다 쓴다.
- 읽은 것만 단정문으로 쓴다. 읽지 못했거나 코드로 닫을 수 없는 것은 단정하지 않고 "확인하지 못했습니다" 한 문장이나 `확인이 필요한 것` 한 줄로 쓴다. 그 밖의 hedge("~일 수 있습니다")는 쓰지 않는다. `항상`·`모두`·`전혀`·`없다`·`뿐`은 끝까지 읽은 것에만 쓴다.
- 운영 절차(누가 승인, 누구에게 요청)는 소스에 있을 때만 쓰고, 아니면 "담당 부서에 확인이 필요합니다"를 한 번만 쓴다.
- 같은 대상을 화면·서버·DB가 검사하면 `핵심 정리` 한 표에 `확인되는 때`(입력할 때 / 저장할 때) 열로 합친다. 층별로 표나 목록을 따로 만들지 않는다. 개수는 표의 행 수와 같다.
- 한 층만 보면 오해할 수 있으면(예: 화면 검증만 통과해도 저장할 때 막힘) 그 한 문장을 `한 줄 답`에 쓴다.
- 읽은 대안 행은 모두 `다른 방법`에 업무 말로 쓴다(번호는 2층 요약표에).

### 2층 (검수용 첨부)

```markdown
---
**검수용 첨부 (코드 근거)**
```

순서: ① `근거 표`(1층 문장마다 한 행) ② 연결된 곳 요약(2절) ③ 항목 표 · 호출 목록 · 조사한 범위 · 조사 대상 표 ④ 주장 검산표 ⑤ 확인하지 못한 부분 ⑥ 더 조사할 곳(2절 번호 질문) ⑦ 확정된 내용(되묻기를 거쳤을 때만 `clarify.md` 블록).

| 번호 | 1층 문장 | 확신도 | 근거 (설명과 `저장소/경로:줄`) | 요약표 번호·읽은 정도 |
|---|---|---|---|---|

- `요약표 번호·읽은 정도`: 그 문장이 기대는 2절 요약표 행 번호와 그 행의 읽은 정도(예: `3·얕게`). 요약표에 없는 곳이면 요약표에 행을 더한 뒤 번호를 쓴다. 코드 밖 정보만 기대면 `-`. 읽은 정도가 `목록만`이면 확신도는 확인 못함이고 1층 문장은 단정하지 않는다.
- 근거 칸은 지금처럼 풀어서 쓴다: 무엇을 읽었고 그 줄이 무엇을 보여 주는지, 식별자와 필드 이름과 메시지 ID를 포함해 쓴다.
- 확신도(확정 / 추론 / 확인 못함)는 이 표에만 쓴다. 한 문장의 확신도는 받치는 근거 중 가장 낮은 값이다.

**조사 대상 표와 요약표**: 요약표는 한 줄 요약이고 조사 대상 표(목록)는 읽은 범위와 비고를 적는 근거용이다. 같은 행의 설명을 두 표에 길게 반복하지 않는다.

**조사한 범위** (근거의 둘째 블록)
- 첫 줄: `연결 조회: <도구> 후보 N개·코드로 확인 M개; …`. 못 쓴 도구는 `<도구>: 쓰지 못함 — <이유>`. 쓰기 테이블이 있으면 `route_impact_candidates: 테이블 n/N개, 접근자 m개(쓰기 w, 읽기·쓰기 x)`도 쓴다.
- `W1:`·`W1b:` 줄과 회차별 신규 건수(`explore.md` 2절), 그 밖의 검색은 `<저장소> <식별자> → n건`.
- 기능·메뉴가 있는지 묻는 질문이면 `메뉴·화면 검색 낱말: <질문의 낱말> / 다른 표현으로 검색한 낱말: <동의어·줄임말 2개 이상>`.
- 개수를 셌으면 `집계 범위·기준: <저장소·glob·검색식> / 전체 N건 / 표에 올린 n건`.
- 고정 줄: `선후행 조회: 배치 행 n개(제외 행 빼고) / 조회 m개(NOT_FOUND로 끝난 시도 포함) / 인자: <name·key·entryPointId 중 쓴 것>`. 배치 행이 없으면 `선후행 조회: 배치 행 0개`. m이 n보다 작으면 답을 내지 않는다.

## 2. 연결된 곳 요약과 더 읽기

2층의 둘째 블록으로 목록의 모든 행(제외 행 제외)을 한 줄씩 요약한다. 화면·API·배치·이벤트·외부를 한 표에 쓴다.

| 번호 | 종류 | 이름 (진입점) | 슬롯 | 하는 일 (한 줄) | 선후행 (배치만) | 읽은 정도 |
|---|---|---|---|---|---|---|

- `이름 (진입점)`: 묶음 행(`impact.md` 3절)이면 그 행의 `진입 job` 목록을 그대로 쓴다.
- `하는 일`: 읽음 행은 읽은 줄, 목록만·못 읽음 행은 `미확인(걸린 줄: 경로:줄)`. 배치는 스케줄 설명과 상태를 같이 쓴다(예: `스케줄 설명: …, 상태: active`).
- `선후행 (배치만)`: `explore.md` 4절 배치 한 줄 요약의 `선행: … / 후행: …` 또는 `조회 안 함(explore.md 4절 사유 둘 중 하나)`. 배치가 아닌 행은 `-`. 배치 행에서 빈 칸이면 답을 낼 수 없다.
- `읽은 정도`: `깊게`, `얕게`, `목록만`(읽지 않은 이유 포함).
- 1층의 `다른 방법`은 이 표의 대안 슬롯 행을 모두 업무 말로 쓰고, 2층 `근거 표`가 이 표의 번호로 가리킨다. 대안이 아닌 관련 행(예: 조직 매핑 재생성)은 표에만 두고 슬롯을 `후속`으로 쓴다.
- 표 위 한 줄: `연결된 곳 N개 중 M개를 읽었고 나머지 K개는 읽지 않았습니다`(N = 목록 행 − 제외 행, K = 목록만·못 읽음 행).
- 더 읽기 질문: 읽지 않은 행과 확인하지 못한 부분 중 **읽을 수 있는 것**만 번호를 붙여 묻는다. 대화형이면 멀티셀렉트(선택지 2~4개 + `그 밖`)로 묻는다. 운영 DB 값처럼 코드로 닫을 수 없는 것은 번호 없이 확인할 위치만 쓴다.

```
더 조사할 수 있는 곳입니다. 번호를 알려 주세요.
6. <무엇을>: <읽으면 답의 어떤 부분이 확인되는지>
권장: n번
```
  사용자가 번호를 고르면 그 행만 같은 깊이로 읽고 이전 답과 달라진 점을 맨 위에 쓴다.
- 영향도 안내(해당할 때만): 답에 쓰기 대상·상태 변화·값 조건·다른 경로가 나왔으면 `이 결과를 바꿀 계획이시면 변경 대상을 알려 주세요. 변경 영향을 따로 조사합니다.`를 쓴다. 나오지 않았으면 쓰지 않는다.

## 3. 해석 두 줄

되묻기 기준을 채우지 않아 한 해석으로 진행했거나, 조사 방법이 갈리는 추상 낱말(원본, 반영, 인식, 정상)이 있으면 쓴다.
- `해석: <고른 해석과 이유>`
- `다른 읽기: <후보 1~2개와 조사 방법의 차이>`. 앵커 후보가 갈렸으면 후보 표(`clarify.md` 1절) 행 번호로 가리키고, 비대화형으로 하나를 고른 경우에는 나머지 행 번호를 메뉴 경로와 함께 모두 쓴다. 후보가 없으면 `다른 읽기: 후보 없음 — <근거 한 줄>`.

## 4. 확신도와 결론

| 표기 | 기준 | 쓰는 곳 |
|---|---|---|
| 확정 | 주장을 받치는 원본 코드 줄을 읽었다(`읽음` 행의 읽은 범위 안, 코드 밖 정보는 그 정보 자체). 이름·위치만 찾은 대상의 동작은 쓰지 않는다 | 결론, 근거 |
| 추론 | 코드로 닫을 수 없는 사유가 있고 읽은 줄에서 논리로 이어질 때만: 소스 없는 라이브러리·외부 시스템, DB 내부 객체, 운영 DB 값, 스케줄러, 업무 의미·정책 | 근거에만 |
| 확인 못함 | 읽을 수 없었거나 찾지 못했다 | 확인하지 못한 부분 (예외: 아래 결론 칸) |

- 설계 초안(`design.md`)의 문장은 확신도 대신 `사실` / `제안` / `가정`으로 구분한다. 확신도 값은 셋뿐이다. 범위 한정은 문장 본문에 쓴다. 읽을 수 있는데 안 읽은 것은 추론이 아니다. 읽거나 `목록만`으로 둔다.
- 1층 문장마다 2층 `근거 표`에 한 행이 있고 확신도는 그 행에 쓴다. 한 행에 확정인 부분과 아닌 부분이 섞이면 둘로 나눈다. 1층에는 확신도를 쓰지 않는다: 확정은 단정문, 추론·확인 못함은 단정하지 않는 한 문장으로 쓴다.

**가능 여부 질문이 1층에 채울 칸** ("~할 수 있나", "어디서 하나", "~는 어디 있나"): `쓸 수 있는가`는 한 줄 답, `어디서`는 이렇게 하세요, `조건`은 막히는 경우, `다른 방법`은 다른 방법 소제목에 쓴다. 칸의 허용 확신도는 아래와 같다.

| 칸 | 쓰는 값 | 허용 확신도 |
|---|---|---|
| 쓸 수 있는가 (첫 줄) | 확정 또는 "확인 못함" + 한 줄 사유. 메뉴·권한 DB 값을 못 읽었으면 확인 못함 | 확정 / 확인 못함 |
| 어디서 | 구현 위치와 실행 진입점. 사용자 화면에서 열리는 곳을 확인하지 못했으면 "구현 위치"라고만 | 확정 / 확인 못함 |
| 조건 | 코드에서 읽은 실행 조건 | 확정 (없으면 `읽은 조건 없음`) |
| 다른 방법(후보) | 요약표의 대안 슬롯 행 전부(번호로 가리키고 한 줄씩. 삭제·종료·취소 질문이면 종료일·사용여부·상태만 바꾸는 UPDATE, 일괄 종료 배치, 이동 화면 포함). 경로가 있다는 사실은 확정, 목적을 이루는지는 업무 정책이라는 사유를 칸에 | 추론 (없으면 `찾지 못함 — W1 UPDATE n건의 SET·WHERE 확인`) |

- 근거에 노출·권한 행을 층별로 둔다: 메뉴 노출 / 버튼 노출 / 서버 권한 검사. 층마다 읽은 줄, 또는 읽지 못한 DB 값과 그 값이 있는 테이블·관리 화면·SQL 위치. 서버 권한 검사는 코드라 읽어서 닫는다. 아래에 "같은 기능이라도 사용자 권한에 따라 보일 수도 안 보일 수도 있습니다"를 한 번 쓴다.
- 함수가 있다는 것과 사용자가 쓸 수 있다는 것은 다르다. 정의 → 주석 아닌 호출 줄 → 실행 경로 → 메뉴 → 버튼 노출 → 서버 권한 검사까지 본 뒤에만 쓴다.
- 날짜 조건은 시작일·종료일·대상 기간을 구분하고 조건의 날짜와 오늘 날짜를 함께 적는다. 화면에서의 차단은 화면 코드에서 확인했을 때만 그렇게 쓴다.

## 5. 근거 표기와 주장 검산표

- 원본 코드: `<저장소>/<경로>:<줄>` 또는 `:<시작>-<끝>`. 모든 행에서 저장소 이름부터 쓴다(`…/`, "위와 같음" 금지). 줄 번호는 직접 읽은 값만.
- 코드 밖 정보: 종류 + 식별자. 예: `테이블 정의: TB_ORDER.ORD_STAT_CD`(주문 상태) / `메뉴 정보: MENU_ORD_01` / `배치 스케줄 정보: ORD_CLOSE_DAILY` / `코드값 정보: ORD_STAT_CD = 10`(접수). 메모리: `메모리(<memoryId>, <종류>, <등록일>)`, 승인된 활성 메모리만.
- 근거 번호는 정수 하나씩. 항목 표·목록의 번호와 따로 매기고, 2층 근거 표는 `조사 대상 n`, `항목 n`, 요약표 번호로 가리킨다.
- 저장·변경 답에는 쓰기 대상 테이블 전부를 SQL id와 함께 쓴다.

**주장 검산표** (열: 번호 / 주장과 근거 번호 / 종류 / 확인한 것 / 확신도. 해당 주장이 없으면 `주장 검산표: 없음`). "확인한 것"이 비면 그 주장을 결론에서 내린다. 행이 없는 개수·부정·"~뿐" 주장은 결론에 쓰지 않는다. 표 안에 세로선 문자를 쓰지 않는다.

| 종류 | 해당 주장 | "확인한 것"에 쓸 것 (빠지면 확인 못함) |
|---|---|---|
| 부정 | 없음, 0건, 호출 없음, 쓰는 곳 없음 | 검색식 원문 / 넣은 동사(INTO·UPDATE·DELETE·MERGE INTO)와 스키마 접두 허용 / W1b 여부 / 대상 범위(저장소·경로·파일 형식) / 잘림 여부. 주장은 이 범위까지만 |
| 실행 | "실행된다, 쓴다, 호출한다, 항상 걸린다, 롤백되지 않는다, 통과한다" | 진입점에서 이어지는 호출 줄(주석 아님) / 감싸는 조건 원문 / 예외를 값으로 돌려주면 호출자가 그 값을 쓰는 방식. 채운 뒤 결론을 조건 원문과 대조해 고친다 |
| 개수 | N개, N곳, N건 | 센 항목을 `저장소/경로:줄`로 모두 나열했고 수가 N과 같음(또는 집계 범위·기준 줄) / 무엇의 개수인지 |
| 단정 | 운영 DB 값에 달린 영향, "이것만", "한 곳뿐", "모두 같다" | DB 값에 달리면 [확정] 금지 / 유일·한정은 목록의 같은 종류 행을 모두 셌고 결론 목록과 같음 |

## 6. 영향·추적 답, 확인하지 못한 부분

- 영향·추적 답의 1층은 `화면에서 / 자동 처리(배치)에서 / 다른 시스템 연동에서` 소제목으로 나누고, 2층 표는 `온라인 / 배치 / 외부`로 나눈다. 해당하는 것이 없어도 한 줄로 쓴다(예: "배치: 세 저장소의 쓰기 검색에서 찾지 못했습니다. [확정]"). 쓰는 방식은 `읽기 / 쓰기 / 조건`, UPDATE·DELETE는 "쓰기(조건 컬럼)". 화면 행에는 화면 title을 함께 쓴다. 외부 행에는 실패 시 동작(오류 전파 / 로그만 남김 / 무시)을 쓴다.
- 확인하지 못한 부분: 항목마다 `무엇을 / 어디를 보면 확인할 수 있는지(파일, 식별자, 담당 영역)`. 원본 코드의 사실("소스가 저장소에 없음", "값이 실행 때 정해짐")은 원인으로 쓸 수 있고 플래티의 한계는 원인으로 쓰지 않는다. 배치의 주기·마지막 실행은 스케줄 정보에 없으면 여기에 쓴다. 한 번의 줄 범위 읽기로 닫히는 것(UPDATE의 SET·WHERE)은 읽어서 닫는다.
- **소스로 답할 수 없는 질문**(운영 데이터 값, 실제 실행 결과): 1층 한 줄 답에 답할 수 없음과 이유, 2층 근거 자리에 "대신 답할 수 있는 것"(그 값이 저장되는 테이블·컬럼·코드값·경로와 위치)을 쓴다.

## 7. 식별자, 쓰지 않는 말

- 2층에서는 식별자 옆에 업무 명칭을 괄호로 쓴다. 예: `ORD1010`(주문 관리). 명칭은 화면 title, 메뉴 label, 테이블·컬럼 comment, 용어 사전에 있는 것만. 없으면 식별자만. 1층에는 업무 말만 쓰고 식별자는 제목의 화면 ID 하나뿐이다.
- 사용자·저장소·API·화면·외부 시스템의 이름을 번역·축약·변형하지 않고 새 약어·라벨을 만들지 않는다. 항목끼리 겹치지 않고 빠짐없이(MECE) 쓴다.

| 쓰지 않는 말 | 대신 쓰는 것 |
|---|---|
| SOT, 생성 문서, spec, EPIC, 분석 결과 | 원본 코드 위치, 또는 코드 밖 정보의 종류 |
| 도구 이름 | 쓰지 않음(예외: 조사한 범위의 연결 조회·`W1:`·`W1b:` 줄) |
| 스킬 내부 용어(직접 경로, 목록 등 단계 이름) | 평이한 서술 |
| 플래티의 한계를 원인으로 삼는 말("분석되지 않아서", "route 후보") | 무엇을 확인하지 못했고 어디를 보면 확인할 수 있는지 |
| 문서와 코드가 다르다는 언급 | 원본 코드 사실만 |

## 8. 답변 예시 (가상)

질문: "잘못 등록한 쿠폰을 지우려면 어디서 하나요?"

```markdown
# 쿠폰 관리 > 일반쿠폰 등록 (CPN2010) — 잘못 등록한 쿠폰 지우기

**한 줄 답**: 「쿠폰 관리 > 일반쿠폰 등록」 화면 위쪽 [삭제] 버튼으로 지울 수 있고, 오늘 등록한 쿠폰만 지워집니다.

**이렇게 하세요**
1. 「쿠폰 관리 > 일반쿠폰 등록」에서 지울 쿠폰 행을 선택합니다.
2. 화면 위쪽 [삭제] 버튼을 누르고 확인 창에서 확인합니다.

**막히는 경우**
- 오늘 등록한 쿠폰이 아니면 지워지지 않습니다.
- 발급 이력이 이미 있는 쿠폰은 지워지지 않습니다.

**다른 방법**
- 「쿠폰 관리 > 쿠폰 종료처리」 배치: 쿠폰을 지우지 않고 종료일만 바꿉니다. 삭제 대신 쓰는 절차인지는 업무 정책이라 코드로 알 수 없습니다.

**확인이 필요한 것**: 이 버튼이 내 화면에 보이는지는 메뉴·권한 설정에 달려 있어 담당 부서에 확인이 필요합니다.

---
**검수용 첨부 (코드 근거)**

| 번호 | 1층 문장 | 확신도 | 근거 | 요약표 번호·읽은 정도 |
|---|---|---|---|---|
| 1 | [삭제] 버튼으로 지운다 | 확정 | 공통 삭제 버튼이 화면의 `cfnDel`을 부르고(`coupon-web/screens/CPN2010.js:180-210`) `POST /api/coupon/delete` → `CouponService.delete`(`coupon-api/.../CouponService.java:60-110`)가 `TB_COUPON`·`TB_COUPON_ISSUE`를 `DELETE`한다(`CouponMapper.xml:42`, `:60`) | 1·깊게 |
| 2 | 오늘 등록한 쿠폰만 | 확정 | 발급일 = 오늘 검사(`CouponService.java:88`). 날짜 비교는 서버에만 있고 화면에는 없다 | 1·깊게 |
| 3 | 발급 이력이 있으면 안 지워진다 | 확정 | `selectIssueCount > 0`이면 예외 `CPN9001`(`CouponService.java:70-80`) | 1·깊게 |
| 4 | 종료 배치가 종료일만 바꾼다 | 추론 | 배치 `closeIssueJob`(스케줄 설명: 쿠폰종료처리, 상태: active)이 `TB_COUPON_ISSUE.END_YMD`만 `UPDATE`(`sql-close.xml:10-28`). 삭제 대신 쓰는지는 업무 정책 | 2·얕게 |
| 5 | 버튼 노출은 설정에 달림 | 확인 못함 | 삭제 버튼 사용 값은 운영 DB 값(`CM_BYMAT_MENU_MPNG.DEL_BTN_USG_YN`)이라 읽지 못함 | - |

(이어서 2층에 연결된 곳 요약 → 항목 표 · 호출 목록 · 조사한 범위 · 조사 대상 표 → 주장 검산표 → 확인하지 못한 부분 → 더 조사할 곳 순서로 쓴다. 표 서식은 2절과 `explore.md`를 따른다.)
```

# 쿠폰 관리 > 일반쿠폰 등록 (CPN2010) — 새 쿠폰을 만들 때 꼭 넣어야 하는 값

**핵심 정리**
| 값 | 조건 | 확인되는 때 | 입력 방법 |
|---|---|---|---|
