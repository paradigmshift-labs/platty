# 변경 영향 조사 흐름 (이 스킬 안에서 한다)

질문이 변경을 전제로 하면 `SKILL.md`의 ①~④ 대신 아래 흐름으로 조사한다. 앵커 확정, 호출 목록, W1, 읽기 규칙은 `explore.md`, 변경 대상 표·핵심 DB·값 판정 서식은 `impact.md`, 답 서식은 `answer-format.md`를 그대로 따른다. 설계를 명시적으로 요청했으면 이 흐름이 끝난 뒤 `design.md`에 따라 설계 에이전트를 부른다.

## 흐름 (변경 영향 조사)

```
준비 → 변경 대상 확정(필요하면 되묻기) → ① 핵심 DB → ② 영향 검색 → ②-2 후보 확인 → ③ 읽기 → ④ 답 초안 → ⑤ 리뷰 → 답
```

**준비** (대화당 1회): `context_status`로 쓸 수 없는 도구를 본다. `workspace_repo_list`의 저장소 이름을 `project-notes.md`와 대조해 이름→repoId 표를 만든다. `code_search_guide_get`을 한 번 읽는다.

**변경 대상 확정**: 질문에서 `무엇을(식별자) + 어떻게(추가·제거·값 변경·삭제)`를 뽑아 `impact.md` 1절 표를 채운다. 변경 대상의 낱말이 가리키는 메뉴·화면·API·테이블 후보가 세는 기능 묶음(`clarify.md` 1절)으로 둘 이상이면 `clarify.md`대로 조사 전에 항상 묻는다. "무엇을"이 비어 있고 조회로 못 채우면 한 번만 묻는다.

**① 핵심 DB** (`impact.md` 2절): 변경이 닿는 데이터를 핵심 5개 이하와 동반 10개 이하로 나눈다. 대상 컬럼·값을 정한다.

**② 영향 검색** (`explore.md` 2절, `impact.md` 3절): 핵심+동반 테이블을 W1로, 대상 컬럼·코드값을 읽고 비교하는 곳을 컬럼·값 검색으로 전체 저장소에 한 번씩 검색한다. 새 항목이 안 나올 때까지 되풀이한다. 걸린 파일을 모두 목록 행으로 만든다.

**②-2 후보 확인** (멀티셀렉트, 후보 진입점이 **7개 이상일 때만**): 영향 검색으로 만든 목록의 진입점(화면·API·배치·외부)을 종류별로 묻는다. 선택지마다 `이름 + 한 줄 설명(후보 설명·스케줄 설명) + 슬롯`을 쓰고, 선택지는 ≤4개(넘으면 가드 > 트리거 > 대안 순으로 4개 + `그 밖 전부`), 기본 선택은 전부다. 6개 이하이면 묻지 않고 모두 조사한다. 비대화형이면 묻지 않고 기본 선택으로 진행하고 조사한 범위에 `후보 확인: 기본 선택으로 진행`을 쓴다(질문 문구와 선택지는 적지 않는다). 사용자가 고르지 않은 진입점은 `목록만`(이유 `사용자 제외`)으로 두고 요약표에 남긴다.

**③ 읽기** (`explore.md` 4절): 목록의 모든 행에 슬롯(트리거·가드·대안·후속)을 붙인다(뜻은 `impact.md` 3절). 검사 함수(가드)가 잡히면 호출자를 **루트 메서드**까지 올라가 루트의 호출 목록을 `explore.md` 1절대로 닫는다. 트리거·가드·대안 행은 개수 제한 없이 메인이 모두 읽고 값 비교 행은 `impact.md` 4절의 판정 서식을 쓴다. 후속 행은 `목록만`으로 두되 배치는 한 줄 요약을 단다.

**④ 답** (`impact.md` 5절, `answer-format.md` 1절): **두 층**으로 쓴다. 1층(현업용)은 한 줄 답과 `고칠 곳 / 깨지는 것 / 확인이 필요한 것`을 `화면에서 / 자동 처리(배치)에서 / 다른 시스템 연동에서`로 나눠 업무 말로 쓰고, 코드 이름·경로·확신도는 쓰지 않는다. 2층 `검수용 첨부`에 근거 표(1층 문장마다 한 행), 연결된 곳 요약표, 호출 목록, 조사한 범위, 조사 대상, 검산표, 번호 질문을 쓴다.

**⑤ 리뷰** (`references/review.md`): 답을 확정하기 전에 서브에이전트(Agent 도구)에게 답 초안을 보내 누락을 점검받는다. 보충 지시는 한 번만 수행하고 답에 반영한다. Agent 도구가 없으면 `리뷰: 생략(도구 없음)`을 조사한 범위에 쓴다.
