# 디자인 팩 검토 화면 설계

`pack_review.py`가 만드는 화면의 정보 구조 계약이다. 이 문서가 바뀌면 생성기를 바꾸고,
생성기가 바뀌면 이 문서를 바꾼다. 특정 팩 한 장을 손보는 문서가 아니다.

## 1. 이 화면의 독자와 할 일

독자는 **디자이너**다. 엔지니어가 아니고, CLI를 매일 쓰지 않는다.

이 화면에서 하는 일은 셋뿐이다.

1. **파악** — 팩이 무엇을 담고 있고, 그래서 4단계 와이어프레임이 무엇을 그릴 수 있는지.
2. **판단** — AI가 합성한 행을 승인·보류·거절한다. 팩의 행 대부분은 사람이 아직 확인하지 않았다.
3. **요청 또는 수정** — 틀린 것을 어디서 어떻게 고치는지 알고 다음 행동으로 넘어간다.

세 번째가 지금까지 비어 있었다. 화면이 "이런 게 있구나"에서 끝나면 디자이너는 다음에 뭘
할지 모른다. **모든 파트는 수정 경로를 함께 보여준다.**

## 2. 공통 파트 골격

모든 파트는 같은 네 블록을 같은 순서로 가진다. 파트마다 구조가 다르면 디자이너가 매번
다시 읽는 법을 배워야 한다.

| 블록 | 답하는 질문 | 출처 |
| --- | --- | --- |
| 무엇인가 | 이 파트가 팩에서 하는 일은? | 이 문서(생성기 상수) |
| 무엇을 판단하나 | 내가 여기서 내려야 하는 결정은? 지금 몇 건 남았나? | `pack_approval.items()` |
| 어떻게 고치나 | 씨앗 파일 · 재생성 명령 · 담당 스킬 | `pack_edit.ROUTES` |
| 내용 | 실제 행 | 팩 |

**수정 경로는 손으로 쓰지 않는다.** `pack_edit.ROUTES`를 읽어서 렌더한다. 두 곳에 같은
내용을 적으면 반드시 어긋나고, 어긋난 안내는 없는 것보다 나쁘다.

## 3. 파트 구성

### 3.0 요약 (맨 위, 새로 추가)

팩 한 장 요약과 **판단 대시보드**. 파트별 미판정 건수와 "어디부터 보면 되는지"를 준다.
미판정이 0이면 이 화면은 조용해야 한다.

### 3.1 토큰

- 판단: 값이 제품과 맞는가. 없는 값이 필요한가.
- 근거: 색 칩과 흰 배경 대비비, 타이포 실물, 간격·radius 막대, 원시 팔레트.
- 수정: **이 저장소에서 못 고친다.** 정본은 HDS `core.tokens.json` / `user.semantic.json`이다.
  그 사실을 파트 머리에 적는다.

### 3.2 컴포넌트

- 판단: 와이어프레임이 쓸 수 있는 목록이 맞는가. 지원 상태 축이 실제로 표현 가능한가.
- 근거 셋을 나란히 둔다.
  1. **엔진 그림** — 4단계가 실제로 내보내는 마크업.
  2. **제품 구현** — 실제 소스를 렌더한 변형(있을 때만). 커밋과 파일 해시를 붙인다.
  3. **계약과 한계** — 인터페이스, 지원 상태, 이 행이 약속하지 않는 것.
- 둘이 다른 이유를 파트 머리에서 한 번 설명한다. 카드마다 반복하지 않는다.
- 수정: `component-promote`(승격), `component-contract`(계약 자체).

### 3.3 화면 역할

- 판단: when·구성·상태·조판 네 문장이 맞는가. 이 역할이 실재하는가.
- 근거: 네 문장, 예외, 연결된 화면 수, 그리고 **AI 합성이라는 표시**.
- 수정: `role` — 씨앗은 `type-guidance.json`이고 `type-rules.json`은 산출물이다.

### 3.4 레시피 규칙

- 판단: must / must_not / optional이 맞는가. 빠진 금지가 있는가.
- 근거: 규칙 문장, 출처(human/extracted/seed), 적용 역할.
- 수정: `recipe`.

### 3.5 원칙과 검사

- 판단: 원칙 33개와 사용성 검사 10개를 유지할지.
- 수정: `principle`, `usability` — 둘 다 정본 파일이라 재생성이 없다.

### 3.6 참조 화면

- 판단: 이 화면을 근거로 삼을지. 역할 지정이 맞는지.
- 근거: 이미지, 출처(Figma 프레임 / 실행 캡처), 라우트와 상태, 한계.
- 실행 캡처는 **디자이너 승인이 아니라 그 커밋의 코드가 만든 결과**임을 행마다 표시한다.
- 수정: `reference`.

### 3.7 판정 기록 (맨 아래, 새로 추가)

판단을 어떻게 남기는지. `pack_approval.py`의 실제 명령을 **이 팩 경로가 채워진 상태로**
보여준다. 승인은 팩 해시에 묶이므로 새 팩에서는 다시 판단해야 한다는 사실도 여기 적는다.

## 4. 화면을 고치는 방법

| 대상 | 파일 | 검증 |
| --- | --- | --- |
| 화면 구조·문구 | `platty-mcp-ba-assistant/engine/pack_review.py` | `platty-mcp-ba-assistant/design-pipeline/src/review-audit.mjs` (빌드가 자동 실행) |
| 제품 구현 미리보기 | `platty-mcp-ba-assistant/design-pipeline/scripts/survey/build-component-preview.mjs` | 렌더 실패 0건 |
| 수정 경로 안내 | `platty-mcp-ba-assistant/engine/pack_edit.py`의 `ROUTES` | 화면이 자동 반영 |
| 판정 항목 | `platty-mcp-ba-assistant/engine/pack_approval.py`의 `items()` | 파트별 미판정 수가 화면에 반영 |

`pack_edit build`는 팩을 만든 뒤 **검토 화면을 렌더하고 감사까지 돌린다.** 발견이 있으면
빌드를 거부하고 팩 디렉터리를 남기지 않는다. 의도한 상태라면 `--allow-render-findings`로
밝힌다. 브라우저가 없는 기계에서는 감사를 건너뛰고 그 사실을 결과에 적는다.

새 파트를 추가할 때는 `PARTS` 상수에 한 항목을 더한다. 렌더 함수만 추가하고 `PARTS`를
빠뜨리면 그 파트는 머리 블록 없이 나오고, 디자이너는 그 파트를 어떻게 고치는지 알 수 없다.

## 5. 유지 규칙

- **단일 파일을 유지한다.** 디자이너에게 전달되는 것은 파일 하나다. 이미지·CSS·미리보기가
  모두 파일 안에 들어가야 옮겨도 열린다(`--self-contained`).
- **팩이 유일한 출처라는 원칙을 지킨다.** 소스에서 온 것(제품 구현 미리보기)은 커밋과 파일
  해시를 달고 "제품 구현"이라고 표시한다. 그 표시가 없으면 팩에 있는 것처럼 읽힌다.
- **한계를 숨기지 않는다.** 행마다의 `limitation`, 미판정 배너, 근거 없는 역할은 그대로 보인다.
- **엔진이 그리지 못하는 것을 그린 척하지 않는다.** 라디오를 체크박스로 그리는 식의 대체는
  하지 않는다. 엔진에 그 노드가 없으면 엔진을 고치거나, 못 그린다고 적는다.
