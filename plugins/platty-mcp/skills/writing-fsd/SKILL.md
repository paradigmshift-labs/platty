# FSD 문서 작성

## 목적과 경계

FSD는 사람이 화면을 검토하고 개발자·구현 AI가 같은 사용자 경험을 만들 수 있게 한다. 승인된 PRD·JTBD의 목표와 정책은 참조하고, **보이는 구성·조건·행동·상태·복구**를 명세한다. API·DB·캐시·SDK·내부 상태 관리 등 기술 설계는 맡지 않는다. 와이어프레임 없이도 화면 디자인 설명만으로 기본·예외 화면을 그릴 수 있어야 한다.

## 작업 순서

1. 최신 사용자 지시와 정정, 승인된 PRD·JTBD·User Story, 디자인시스템, 현행 서비스의 관련 증거를 확인한다. 출처·버전·확인 범위를 기록한다. 연결된 서비스에 적용되는 조회 지침을 따른다. 사실, 해석, 설계 가정, 사람의 결정을 분리한다. 사용자가 금지한 자료는 열지 않는다.
2. 변경되는 화면·요소·흐름을 찾고, 기존 자료의 답을 회수한다. [문답 기준](references/interview.md)의 모든 축을 조사해 **결정 공백 대장**을 만든다. 기존 답을 다시 묻지 않되, 자료에 없는 제품·디자인 선택을 AI가 채우지 않는다.
3. 비디자이너가 답할 수 있는 말로 대안을 설명하고 관련 질문을 **한 번에 보통 8~10개** 묻는다. 한 질문에는 한 판단을 둔다. 추천의 이유·손실을 보이고 누를 수 있는 선택지와 직접 답변 경로를 제공한다. 추천의 사전 선택·무응답·UI 닫힘은 답변이 아니다. [문답 기준](references/interview.md)에 따라 번호와 미응답을 보존하고, 답변마다 공백을 재조사한다.
4. 화면·동작이 정리되면 [측정 의도 인계 기준](references/measurement-handoff.md)에 따라 PRD의 최종 목표와 FSD의 핵심 흐름을 연결한다. AI가 과정지표와 그 계산 의미·해석 한계를 직접 선정해 개발자에게 인계한다. **측정·이벤트에 관한 문답은 별도 단계에도 일반 문답에도 넣지 않는다.** 개발자가 이벤트 텍소노미와 계측 가능성을 설계한다.
5. [형식 기준](references/fsd-format.md)과 [작성 골격](assets/fsd-template.md)에 따라 11개 장과 부록 A~E를 작성한다. 확정·승계·적용안·제안·미결정·확인 필요·해당 없음을 구별한다. 미결을 구현 명령으로 쓰지 않는다. 문답 중 수정 보류 지시가 있으면 문답 종료까지 문서를 바꾸지 않는다.
6. [검수 기준](references/verification.md)으로 결정 누락, 화면의 시각적 재구성, 동작의 구현 가능성, ID·링크·목차를 확인한다. 필수 선택이 남은 범위는 `구현 결정 대기`로 표시하고, 확정된 범위의 작성·검토는 계속한다.

## 완료 판정

**문답 완료**는 알려진 설계·제품 결정 공백이 답변·명시적 보류·사실 확인 필요·해당 없음으로 모두 분류된 상태다. 측정 의도는 문답 완료의 조건이 아니며 AI가 작성한다. **개발 전달 가능**은 필수 화면·동작에 사람의 제품 선택이 남지 않은 범위에만 붙인다. 초안, 추천, 기대 시나리오를 승인·구현·검증 완료라고 주장하지 않는다.
