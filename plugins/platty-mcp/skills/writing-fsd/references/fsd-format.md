# FSD 형식과 작성 기준

## 문서 계약

고정 필드형 Markdown을 기본으로 한다. 문서 앞에 실제 이동하는 목차와 독자별 읽는 순서를 둔다. PRD·JTBD의 목표·사용자·정책은 버전·항목 ID로 참조하고 반복 설명하지 않는다. **변경되는 기존 화면**은 다루고, 변경 없이 연결만 되는 화면은 목록과 이동 관계만 적는다. 확인되지 않은 예외 화면·경로를 새로 만들지 않는다. 와이어프레임 첨부는 필수가 아니다.

| 본문 장 | 필수 역할 |
| --- | --- |
| 1. 적용 범위와 참조 문서 | 문서 상태·버전, 변경 범위, 참조 문서의 버전·항목·링크 |
| 2. 추가·변경되는 개념과 용어 | 현재 이해와 목표 개념의 차이, 화면에서 사용할 명칭·설명 |
| 3. 화면 목록과 사용자 실행 흐름 | 변경/연결 화면, 진입·분기·완료·취소·뒤로·재진입 |
| 4. 화면별 구성과 배치 | 화면→영역→요소, 읽는 순서·위치 관계·문구·상대적 강조·상태별 모습 |
| 5. 컴포넌트별 상호작용과 시간 규칙 | 노출·활성 조건, 계기→반응→다음 상태, 시간·반복·겹침 |
| 6. 기능 정책의 화면 적용과 입력 규칙 | PRD 정책의 화면 적용, 입력 기본값·범위·검증·수정·취소 |
| 7. 화면 정보의 표시·유지·갱신 | 의미·단위·표기·결측·길이·최신성·유지·복원·갱신 |
| 8. 사용자에게 보이는 상태·예외·복구 | 최초·로딩·빈 값·완료·실패·부분 성공, 안내·재시도·복원 |
| 9. 디자인시스템 적용과 공통 표현 조건 | 확인된 컴포넌트·변형·토큰, 좁은 화면·큰 글씨·접근성 |
| 10. 설계 가설과 의사결정 근거 | 가설·전제·근거·반론·대안·추천·사람의 선택·남은 가정 |
| 11. 기대 결과와 미결정 사항 | 정상·경계·예외·복귀 시나리오, 기대 효과와 과정지표 ID 연결, 미결의 영향·담당·시점 |

부록 A는 **과정지표와 측정 의도**(PRD 목표·FSD 가설, 핵심 단계별 지표, 대상·분자·분모·관찰 범위, 화면·동작·상태 ID, 해석 한계, 개발자 계측 설계 인계), B는 PRD/JTBD→개념→화면→요소→동작→결정·시나리오의 참조 관계, C는 출처·버전·적용 조건·한계가 있는 설계 근거, D는 추가·변경 용어 색인, E는 질문·결정·변경·대체 이력이다. 부록 A는 AI가 [측정 의도 인계 기준](measurement-handoff.md)에 따라 작성한다. 이벤트 이름·발생 조건·속성 등 실제 텍소노미는 개발자가 설계한다.

## 필드와 ID

화면, 영역, 요소, 흐름, 배치, 동작, 시간, 정책 적용, 입력, 정보, 유지, 갱신, 상태, 복구, 표현, 가설, 대안, 결정, 시나리오, 측정 의도, 근거에 **문서 안에서 고유하고 안정적인 ID**를 부여한다. 접두어 예: `SCR-01`, `AREA-01`, `EL-01`, `FLOW-01`, `LAY-01`, `ACT-01`, `TIME-01`, `POL-01`, `INPUT-01`, `INFO-01`, `KEEP-01`, `REFRESH-01`, `STATE-01`, `REC-01`, `DS-01`, `HYP-01`, `ALT-01`, `DEC-01`, `SCN-01`, `MEAS-01`, `EVD-01`. 같은 대상의 이름·문구만 바뀌면 ID를 유지한다. 한 규칙의 원문은 한 곳에 쓰고 다른 절에서는 ID로 연결한다. 요약·예시·시나리오가 별도 규칙으로 변하지 않게 한다.

| 상태 | 작성 의미 |
| --- | --- |
| 확정 | 사람의 명시적 답변·정정. 질문 번호·결정자·일자를 연결 |
| 승계 | 충돌하지 않는 승인된 기존 규칙. 원문과 적용 범위를 연결 |
| 적용안 | 확정·승계를 화면에 풀어 쓴 표현. 새 선택이 들어가면 사람에게 질문 |
| 제안 | AI 추천, 미채택. 구현 기준에서 제외 |
| 미결정 | 사람의 판단 대기. 영향받는 화면·규칙·후속 질문 기재 |
| 확인 필요 | 서비스 사실·자산·측정 가능성의 외부 확인. 담당·시점 기재 |
| 해당 없음 | 적용되지 않음. 자명하지 않으면 이유 기재 |

## 화면을 사람이 읽는 방식

각 변경 화면의 첫 부분은 짧은 글로 **사용자가 무엇을 어디서 보고 무엇을 먼저 하는지** 설명한다. 화면 전체의 영역, 요소의 상하·좌우·포함 관계, 그룹, 읽는 순서, 주·보조 행동, 기존·신규 요소의 상대적 강조를 정의한다. 정확한 문구·이미지·배지·버튼과 긴 문구·사진 없음·숫자 없음·좁은 화면·글자 확대의 표현을 적는다. 상태별로 `유지 / 추가 / 변경 / 숨김 / 조작 가능`을 비교한다. 상세 규칙은 ID로 연결한다. `근처`, `적절히 강조`, `겹치지 않게`처럼 여러 화면이 가능한 표현은 구체화하거나 미결로 남긴다. 디자인시스템의 확인된 값과 새 선택을 구별하고 미확정 색·치수를 꾸미지 않는다.

## 구현 AI가 읽는 방식

각 동작에 `대상 → 현재 상태·전제 → 발생 계기 → 보이는 반응·정확한 이동 대상 → 다음 상태`를 둔다. 적용될 때는 노출/활성 조건, 입력 기본값·범위·검증 시점·오류 문구, 뒤로·취소·복귀·재진입, 시간 값·단위·시작·중단·초기화·재시작·화면 이탈, 반복 클릭·동시 사건·대상의 상태 변경, 성공/실패 뒤 정보·스크롤·포커스·읽음·선택의 유지를 기록한다. 정상만 아니라 빈 값·로딩·부분 데이터·오류·복구를 다룬다. 사용자에게 보이는 결과가 미정이면 내부 구현 제안으로 메우지 않고 질문으로 되돌린다.

## 문장과 구조

`# → ## → ### → ####`는 실제 포함 관계를 표현한다. 형제 제목을 억지로 들여쓰지 않는다. 긴 문장은 조건·기본 상태·예외·전환을 부모/자식 불렛으로 나눈다. 서로 관련된 불렛을 들여써 그룹 관계를 보인다. 목록·상태 비교는 가로 표, 조건이 많은 단일 동작·상태·결정은 `항목 | 내용` 세로 표, 맥락은 짧은 본문으로 쓴다. 한 셀에 독립 규칙 여러 개를 넣지 않는다. 낯선 개발 용어는 쉬운 말로 풀되 정확한 ID·코드명·추적 용어는 보존한다. 이해 가능한 디자인 용어 `CTA`를 기계적으로 바꾸지 않는다. `(내용없음)` 같은 빈 템플릿 표시는 최종본에서 제거한다.

목차 링크는 Markdown/Codex와 Notion에서 생성 방식이 다를 수 있다. 실제 전달하는 **각 환경에서 클릭해** 제목 이동을 확인한다. Notion으로 옮기면 그 페이지의 실제 제목/목차 블록에 맞춘다. 클릭 검증을 못 했다면 검증했다고 쓰지 않는다.
